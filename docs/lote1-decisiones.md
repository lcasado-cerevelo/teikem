# Lote 1 — Capas transversales A-I + módulo 0B: qué se construyó y decisiones a revisar

## Mapa de lo construido

| Capa | Tablas | Código principal | Endpoints |
|---|---|---|---|
| A. Catálogos | CatalogDomain, LookupCode, LookupCodeOverride (+ `TenantId` opcional en ambas, ext. 0002) | `LookupService`, `LookupCache`, `MultilingualText` | `/api/v1/catalogs/*` |
| B. Estatus | StatusCode, StatusCodeOverride, StatusLateralEntry, StatusCapability, EntityStatusHistory | `StatusService` (pipeline, capacidades, laterales, `TransitionAsync`, validador al guardar, efectos `IStatusTransitionEffect`) | `/api/v1/status/*` |
| C. Contactos | ContactPoint | `ContactPointService` + `IOwnedEntityResolver` (pertenencia por EntityType) | `/api/v1/contacts/*` |
| D. Seguridad | AspNet* (0001), UserTenant, Permission, Role, RolePermission, UserRole, **UserPermission** (ext.), UserDataScope, UserMfaFactor, MfaRecoveryCode, RefreshToken | `AuthService`, `JwtTokenService`, `TotpService`, `PermissionService`, `UserAdminService`, policies `[RequirePermission]`, `[RequireAal2]`, `[RequireModule]` | `/api/v1/auth/*`, `/me`, `/roles`, `/permissions`, `/users/*` |
| E. Auditoría | AuditLog, EntityStatusHistory, SecurityEvent | `AuditSaveChangesInterceptor` (diff + CorrelationId), `SecurityEventWriter` (scope propio), `AuditQueryService` (actividad unificada + CSV) | `/api/v1/audit/*` |
| F. Campos personalizados | CustomFieldDefinition, CustomFieldOption, CustomFieldValue | `CustomFieldService` (EAV tipado, requerido/único/DSL/opciones/lista de catálogo) | `/api/v1/custom-fields/*` |
| G. Vistas | ReportDefinition (+ `IsSystem`, `SecondaryJson` ext.), ReportShare | `AnalyticsEngine` (fuentes combinables, filtros DSL, agrupación multi-campo, totales, orden, campos personalizados como columnas), `AnalyticsService` | `/api/v1/analytics/reports/*` |
| H. Indicadores | **IndicatorDefinition, IndicatorShare** (ext.) | mismo motor; visibilidad TENANT/PRIVATE/SHARED; `analytics.dates` | `/api/v1/analytics/indicators/*` |
| I. Gráficos | **ChartDefinition, ChartShare** (ext.) | mismo motor; BAR/DONUT (top 8) y LINE (cronológico, últimos 30) | `/api/v1/analytics/charts/*`, `/analytics/pulse` |
| 0B. Plataforma | Tenant (+ defaults, MFA/sesión, marca), TenantHoliday, ModuleDefinition (+ `IsCore`, 13 módulos), TenantModule | `ModuleService` (dependencias, cascada, núcleo), `TenantService` (ajustes, calendario laboral), `ProvisioningService` | `/api/v1/modules`, `/tenant/*`, `/platform/tenants` |
| Preferencias | **UserAnalyticsPreference** (ext.) | "Pulso del día por usuario": rango y switch de Pulso por usuario con la definición como default | `.../my-date-range`, `.../my-pulse` |

Todo `TenantId` sale del JWT (`tid`); el filtro global de EF Core (`TeikemDbContext.BuildTenantFilter`) se aplica a toda entidad `ITenantScoped`/`IOptionallyTenantScoped`. Defensa en profundidad: filtro (datos) + `[RequirePermission]` (acción) + resolvers de pertenencia (recurso).

## Cómo se prueba

1. `docker compose up -d sqlserver` y `dotnet run --project src/Teikem.Api -- db-init`.
   Deben quedar aplicados en `dbo.__SchemaVersion`: `0001_identity.sql`, `logistica-db-estructura.sql`, `logistica-db-seed.sql`, `0002_lote1_extensiones.sql`; luego el seeder de permisos (38 códigos) y el tenant demo.
2. `dotnet test` — pruebas unitarias del DSL (incl. comparación de fechas), TOTP (vectores RFC 6238), etiquetas, rangos y agregados.
3. Con el API arriba (Swagger en `/swagger`):
   - `POST /api/v1/auth/login` `{ "email": "admin@teikem.local", "password": "Teikem_Admin_2026!" }` → `status: ok` + tokens.
   - `GET /api/v1/me` → permisos efectivos (TenantAdmin = todos) y módulos encendidos de Advance (COD, WMS_LOTSERIAL, RENTAL_EQUIPMENT, CLIENT_PORTAL, CUSTOM_FIELDS, PURCHASING, CATALOG, ANALYTICS, SYSTEM, LTL_GROUND; apagados CROSSDOCK, MARITIME, RENTAL_BILLING).
   - `GET /api/v1/catalogs/OrderStatus` (con `X-Lang: en` cambia el idioma) y `PUT /catalogs/ServiceType/EXPRESS/override` → renombrar para el tenant.
   - `GET /api/v1/status/OrderStatus`, `PUT /status/OrderStatus/INBOUND/override {"isEnabled":false}` (Caguas: pipeline solo delivery) y `PUT .../DRAFT/override {"isEnabled":false}` → 422 "Pipeline inválido" (sin etapa inicial).
   - `PUT /api/v1/modules/CROSSDOCK {"isEnabled":true}` → exige AAL2: `POST /auth/reauth` con la contraseña y reintentar con el nuevo access token. `PUT /modules/RENTAL_BILLING` sin RENTAL_EQUIPMENT → 409; `PUT /modules/LTL_GROUND {"isEnabled":false}` → 409 (núcleo).
   - `POST /api/v1/custom-fields/definitions/USER` `{ "fieldKey":"cost_center","labels":{"es":"Centro de costo","en":"Cost center"},"dataType":"TEXT","isRequired":false,"isUnique":true,"showInList":true,"validationJson":"{\"regex\":\"^CC-\\\\d{3}$\"}" }` y `PUT /custom-fields/values/USER/1 {"values":{"cost_center":"CC-100"}}` (con `"CC-1"` → 400 con el error por campo).
   - `GET /api/v1/analytics/pulse` → indicadores/gráficos de sistema calculados sobre AuditLog/SecurityEvent/Users (cada llamada autenticada ya deja rastro). `POST /analytics/reports/AUDIT_LOG/preview` con columnas `["CreatedAtUtc","Action","User.FullName"]` y `secondary: ["User"]` prueba la combinación muchos-a-uno.
   - `GET /api/v1/audit/activity` muestra los cambios de arriba con su `correlationId` (cabecera `X-Correlation-Id` de la respuesta) y los eventos LOGIN/REAUTH/PERMISSION_DENIED; `GET /audit/activity/export.csv` baja el CSV.
   - Con `despacho@teikem.local`: `GET /api/v1/users` → 403 y queda un `PERMISSION_DENIED` en `/audit/security-events` (visto como admin).
   - MFA: `POST /auth/mfa/totp/enroll` → secreto/otpauth; `POST /auth/mfa/totp/confirm {"code":"123456"}` con un autenticador → códigos de recuperación; el siguiente login devuelve `mfa_required` y `POST /auth/mfa/verify` (Bearer = challenge token) completa.

> Cómo se ejecutó realmente: el contenedor de trabajo no tenía salida a los hosts de .NET ni de SQL Server, así que los pasos 1-3 se ejecutaron en **GitHub Actions** (`.github/workflows/ci.yml`: SQL Server 2022 como servicio, `dotnet build`, `dotnet test`, `db-init` y `scripts/smoke.sh`). La corrida verde está en https://github.com/lcasado-cerevelo/teikem/actions/runs/36053300602. El smoke test recorre login → /me → catálogos → estatus → módulos (AAL2) → ajustes → campos personalizados → análisis/Pulso → auditoría/CSV → RBAC (403 + PERMISSION_DENIED) → refresh/rotación/logout; se puede correr igual en local con `scripts/smoke.sh http://localhost:5000`.

## Decisiones tomadas (revisar)

1. **Esquema: scripts SQL versionados en vez de migraciones EF.** El README de Diseño exige la BD separada del API y los scripts de `Diseño/` no son idempotentes (la estructura hace `CREATE TABLE` sin guardas). Se construyó `SqlScriptRunner` + `dbo.__SchemaVersion` (nombre + hash) que aplica `0001_identity.sql` (equivalente a la migración inicial de Identity, hecha a mano), `Diseño/logistica-db-estructura.sql`, `Diseño/logistica-db-seed.sql` y `db/migrations/0002+`. EF Core se usa solo como ORM. Si prefieres migraciones EF para Identity/extensiones, se generan con `dotnet ef migrations add` una vez haya SDK; el modelo ya está mapeado 1:1.
2. **Tablas/columnas nuevas (0002_lote1_extensiones.sql)** que el documento describe pero el SQL no tenía: `IndicatorDefinition`/`IndicatorShare`, `ChartDefinition`/`ChartShare`, `UserPermission` (permisos extra por usuario), `UserAnalyticsPreference` (Pulso/rango por usuario), `ReportDefinition.IsSystem`/`SecondaryJson`, `Tenant.DefaultServiceTypeLookupId`/`DefaultPackageTypeLookupId`/`MfaRequired`/`Aal2WindowMinutes`/`SessionDays`/`BrandingJson`, `ModuleDefinition.IsCore` + módulos CATALOG/ANALYTICS/SYSTEM (catálogo de 13), `CatalogDomain.TenantId`/`LookupCode.TenantId` (listas propias del tenant), `AspNetUsers.IsPlatformAdmin`, dominios `AggregateFn`, `BusinessModule`, `DateRangeMode`, `PackageType` y códigos extra de `EntityType`/`SecurityEventType`/`PermissionCategory`. Conviene incorporarlos al script de estructura oficial en la próxima revisión del diseño.
3. **Listas del tenant con `DomainKey = T{tenantId}_{SLUG}`** porque `UQ_CatalogDomain(DomainKey)` es global. Alternativa: cambiar la unicidad a (TenantId, DomainKey) en el esquema.
4. **Permisos: 38 códigos** = los 31 del seed + `admin.audit`, `admin.customfields`, `admin.statusconfig`, `analytics.view`, `analytics.manage`, `analytics.dates` (el `analitica.fechas` del mock) y `contacts.manage`. Categoría nueva `ANALYTICS`. Las plantillas de rol se completan desde código (`PermissionCatalog.RoleTemplates`); el seed SQL sigue siendo compatible.
5. **Administrador de plataforma** (`IsPlatformAdmin`): opera cualquier tenant sin membresía, tiene todos los permisos y sus acciones quedan atribuidas a su usuario en AuditLog/SecurityEvent del tenant (visible para el tenant). Solo él edita catálogos globales y aprovisiona tenants.
6. **Reglas de transición** (`StatusService.TransitionAsync`): pipeline solo avanza a la siguiente etapa habilitada por `SortOrder`; lateral/terminal fuera de orden exige `StatusLateralEntry` (regla del tenant pisa la default; sin reglas = permitido); desde un lateral solo se vuelve a la etapa desde la que se desvió (o la siguiente); terminal no sale. El validador de pipeline corre al guardar overrides, no en cada transición. Sin `StatusCapability` configurada = acción permitida.
7. **Motor de análisis en memoria** (`AnalyticsEngine`): las fuentes pre-filtran por fecha y tope de 20k filas; filtros/joins/agrupación se evalúan en C#. Suficiente para el Lote 1 y para el tamaño de Advance; cuando llegue Órdenes/Inventario se puede empujar filtros a SQL sin cambiar los contratos. Las fuentes del Lote 1 son AUDIT_LOG, SECURITY_EVENT y USER; cada lote registra las suyas (`IDataSource`).
8. **DSL propio** (`RuleEvaluator`): `and/or/not` anidado + operadores tipados (eq, ne, gt, gte, lt, lte, contains, startsWith, endsWith, in, notIn, between, isNull, notNull, isTrue, isFalse) y validación `{regex,min,max,minLength,maxLength}`. No tengo el DSL de SEPHAS; cuando lo compartas se ajusta la sintaxis para la paridad TS/C# (el evaluador está aislado en un solo archivo).
9. **Pulso/rango por usuario** implementado como pide la nota "Pulso del día por usuario": `my-date-range`/`my-pulse` son preferencia personal sin permiso especial; `default-date-range` cambia la definición y exige dueño o `analytics.dates`. Gráficos también tienen visibilidad (TENANT por defecto) para no divergir de Indicadores.
10. **Contraseñas** según NIST 800-63B: mínimo 12, sin composición, lockout 5/15 min, PBKDF2 con 600k iteraciones (Argon2id requiere un paquete NuGet; se puede cambiar el `IPasswordHasher` sin tocar el resto). HIBP queda como `IPasswordBreachChecker` no-op (necesita salida a Internet).
11. **JWT propio**: access token de 15 min con `tid`, `sid` (sesión), `ss` (hash del SecurityStamp, validado por request con caché de 60 s → logout global/cambio de contraseña invalidan tokens vivos), `aal2` (instante del último step-up); refresh token aleatorio, hasheado, rotado en cada uso y con detección de reutilización (revoca la cadena). SMS de respaldo y biometría no se implementan en este lote (no hay proveedor); TOTP + códigos de recuperación sí.
12. **Auditoría**: `AuditLog.EntityId` para llaves compuestas (TenantModule) va en 0 y la llave completa en `ChangesJson.$key`. Las entidades sin `[AuditEntity]` (RefreshToken, MfaRecoveryCode, AuditLog, SecurityEvent, EntityStatusHistory, CustomFieldValue, UserAnalyticsPreference) no generan bitácora por diseño.
13. **Aprovisionamiento** (`ProvisioningService`): tenant + módulos núcleo/default (LTL_GROUND, SYSTEM, CATALOG, ANALYTICS, CUSTOM_FIELDS) + pedidos con dependencias + clon de las 6 plantillas de rol + admin con `TenantAdmin` + vistas/indicadores/gráficos de sistema. El seed SQL de `TenantModule` para el tenant demo no aplica en BD limpia (no existe tenant al correrlo); lo hace `DemoTenantSeeder`.
14. **Hallazgos en los scripts de Diseño**: (a) el script de estructura **no creaba en SQL Server** por dos FKs: `RentalContract.ContactId` apuntaba a `dbo.Contact` (inexistente; es `dbo.ClientContact`) y `RentalCharge.InvoiceId` apuntaba a `dbo.Invoice` antes de crearla — **estos dos sí se corrigieron en `Diseño/logistica-db-estructura.sql`** (cambio mínimo, la FK de Invoice pasó a un `ALTER TABLE` después de crear Invoice), porque sin ellos el script no corre; (b) el script de estructura no es idempotente (contradice el README de Diseño), por eso el runner lo aplica una sola vez por hash; (c) `Tenant.DefaultServiceTypeLookupId/DefaultPackageTypeLookupId` y el dominio `PackageType` (módulo 2) no existían — cubiertos en `0002`; (d) el bloque de `TenantModule` del seed no aplica en BD limpia porque todavía no hay tenant — lo hace `DemoTenantSeeder`. Los cuatro documentos de detalle que cita el README de Diseño (fase1-v3, módulos 4-6, módulos restantes, seguridad-auditoría) no están en el repo.

## Lo que queda fuera de este lote (a propósito)
- Portal (`UserKind=PORTAL`): el login lo rechaza; su superficie llega con el módulo 10.
- `UserDataScope` se guarda y expone en `/me`, pero el filtro adicional por almacén/cliente se aplica cuando existan esas entidades (Lotes 2 y 6).
- Programación de informes (`ScheduleCron`/`DeliveryEmails`) se persiste; el job de envío por correo no está construido.
